🏛️ Master Schema (Option B: Unified People + Bridge Table) Active Engine
1. people (Directory)
PK: id | Name, Phone, Address, A-Number, SSN, DOB, Citizenship
2. cases (Fact Hub)
PK: case_id | FK: assigned_attorney_id → people.id | status, version
3. case_parties (Bridge)
FK: case_id → cases.case_id | FK: person_id → people.id | role_type
4. audit_logs (Security)
FK: case_id → cases.case_id | version, actor, action, details, timestamp
Session Auth Flow (Why the Sign-In Screen Exists) Trust Boundary
1. Sign In
POST /api/login {username} → server inserts row in sessions (token → person_id) and returns the token.
2. Browser Holds Token
Stored in localStorage atlas_session. Every POST sends Authorization: Bearer <token>.
3. Server Resolves Identity
token → sessions → people row → actor + role. Identity claimed in the request body is IGNORED — the client is never trusted.
4. Enforcement
FSM checks the session role per action. Missing/invalid token → 401 → sign-in overlay. Prototype gaps: no passwords, no session expiry.
